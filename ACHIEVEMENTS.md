# Achievement checklist

This file explains which GitHub profile achievements this project can genuinely
help you earn, which ones it cannot, and exactly what each person has to do.

---

## Read this part first

**GitHub does not officially document the achievement list or its thresholds.**
The [official profile reference][docs-profile] describes Achievements as a
*public preview* feature, explains only how they are displayed, and names
exactly one achievement — Mars 2020 — in order to say it has ended.

Everything in the "requirement" column below comes from maintained community
sources, not from GitHub documentation. **The thresholds can change without
notice, and GitHub has changed them before.** Treat this file as a good guess
that was accurate when it was written, not as a contract.

Nothing here is worth a suspended account. Every route in this document is a
real contribution. If a step ever feels like it is manufacturing activity rather
than doing work, stop and re-read the [Code of Conduct](CODE_OF_CONDUCT.md).

## The rotation

Every contribution has four **roles**:

| Role | What they do |
|---|---|
| **Reporter** | Opens the issue describing one real improvement |
| **Builder** | Creates the branch, makes the change, opens the pull request |
| **Reviewer** | Reads the diff and approves or requests changes |
| **Merger** | Merges it once the check is green and the review is in |

Two rules that never change, no matter how many people are involved:

* **The Builder is never the Reviewer.** A review of your own work is not a
  review.
* **The Builder never merges their own pull request** — with exactly one
  exception, the YOLO step, where that is the entire point.

### Rotation A — two active participants (start here)

With two people, one person builds and the other does everything around it.
Swap every round.

| Round | Reporter | Builder | Reviewer | Merger |
|---|---|---|---|---|
| **1** | @Isaiahchonchoramirez | **@Indicaza** | @Isaiahchonchoramirez | @Isaiahchonchoramirez |
| **2** | @Indicaza | **@Isaiahchonchoramirez** | @Indicaza | @Indicaza |
| **3** | @Isaiahchonchoramirez | **@Indicaza** | @Isaiahchonchoramirez | @Isaiahchonchoramirez |
| **4** | @Indicaza | **@Isaiahchonchoramirez** | @Indicaza | @Indicaza |

Reviewer and Merger being the same person is fine and completely normal — it is
how most two-person projects actually run. What matters is that it is not the
Builder.

After four rounds each of you has built twice, which is the **2 merged pull
requests** Pull Shark needs, and has reviewed and merged twice.

### Rotation B — three participants (once @izawawi joins)

### If a fourth person joins

Split Reviewer and Merger apart and give each their own seat:

| Round | Reporter | Builder | Reviewer | Merger |
|---|---|---|---|---|
| **1** | Person A | Person B | Person C | Person D |
| **2** | Person B | Person C | Person D | Person A |
| **3** | Person C | Person D | Person A | Person B |
| **4** | Person D | Person A | Person B | Person C |

Write the current round's assignment into the **Role rotation** section of the
pull request template so nobody has to remember whose turn it is.

### 1. Pull Shark — everyone

**Requirement (community-sourced):** 2 merged pull requests for the base badge.
Tiers at 2 / 16 / 128 / 1024.

**What each participant does**

1. Take your turn as "Writes the PR" in the rotation.
2. Follow [CONTRIBUTING.md](CONTRIBUTING.md) end to end: branch, change,
   validate, commit, push, open the pull request.
3. Your first one is your contributor card. Your second is a real task from the
   [Other things you can contribute](CONTRIBUTING.md#other-things-you-can-contribute)
   list.

**Who does what**

* **Reporter** opens the issue.
* **Builder** writes the pull request — **this is the person who earns the Pull
  Shark credit**, so the Builder seat is the one that has to rotate fairly.
* **Reviewer** reviews it.
* **Merger** merges it.

In [Rotation A](#rotation-a--two-active-participants-start-here), that means
round 1 gives the Pull Shark credit to @Indicaza and round 2 gives it to
@Isaiahchonchoramirez.

**Repeatable?** Yes. Everyone needs **2** merged pull requests for the first
badge. 16 gets the next tier, which two or three people can reach together
over a few weeks of real work — but only if there is real work. Do not
manufacture pull requests to chase 16.

**Delay:** up to 24 hours after the second merge.

**Uncertainty:** low. This is the best-documented achievement of the set.

**Doing it honestly:** each pull request must change something a person would
actually want changed. A typo fix is a legitimate pull request. An empty commit
is not. Splitting one change across five pull requests to inflate the count is
not.

### 2. Pair Extraordinaire — everyone, in pairs

**Requirement (community-sourced):** a co-authored commit inside a merged pull
request. Tiers reported at 1 / 10 / 24 / 48.

**What each participant does**

1. Pair up with someone. Actually work together — a call, a shared screen, or
   one person writes and the other reviews live. The credit is for genuine
   collaboration.
2. Ask your partner for their GitHub **no-reply** email. They find it at
   <https://github.com/settings/emails>. **Never guess it, and never lift it
   from an old commit log without asking.**
3. Whoever is at the keyboard commits with the trailer:

```bash
git commit \
  -m "SHORT SUMMARY OF THE CHANGE" \
  -m "Co-authored-by: CO_AUTHOR_NAME <CO_AUTHOR_NOREPLY_EMAIL>"
```

4. Verify before pushing:

```bash
git log -1 --format=full
```

The trailer must be the last block of the message, after a blank line, spelled
exactly `Co-authored-by:`.

5. Push and open the pull request. Once merged, **both** people get credit.
6. Swap seats and do it again the other way round, so both of you have driven.

**Who does what**

* **Reporter** opens the issue.
* **Builder** and one other person write it **together** — one of them commits,
  and the `Co-authored-by:` trailer credits both.
* **Reviewer** reviews it. Ideally someone who did *not* write it.
* **Merger** merges it.

**With only two active participants, be honest about the review.** If
@Isaiahchonchoramirez and @Indicaza co-author a pull request, there is no
third person to review it. Two workable options, both fine:

* The co-author who did **not** open the pull request reviews it. GitHub allows
  this — they are a commit co-author, not the pull request author. Say so in the
  review comment: *"I paired on this, so this is a second read rather than a
  fresh review."* Honest, and the automated check still has to pass.
* Or merge it unreviewed, and note in the description that it was paired work on
  a small change. Do not make this the habit for anything non-trivial.

Once @izawawi joins, this stops being a problem — pair up and let the third
person do a genuine independent review.

**Repeatable?** Yes, four tiers. Every pair should do at least two so nobody is
stuck on the uncertain first-tier threshold.

**Delay:** up to 24 hours after merge.

**Uncertainty:** medium — the first tier may be 1 or 10 co-authored pull
requests. Assume 10 is possible and keep pairing on real work.

**The failure mode to watch for:** if the email is not attached to the
co-author's GitHub account, GitHub shows the name as plain text with no avatar
and awards nothing. Check the merged commit on GitHub: two avatars means it
worked.

**Doing it honestly:** only add a `Co-authored-by` trailer for someone who
genuinely contributed to that commit. Adding a friend's name to work they did
not touch is falsifying authorship.

### 3. YOLO — everyone, once, before branch protection is enabled

**Requirement (community-sourced):** merge a pull request without a code review.

**Why this is safe here:** merging without review is normally a bad habit. It is
acceptable for exactly one category of change: a small, self-contained,
non-breaking edit that the automated check already validates. Everyone gets one.

**What each participant does**

1. Pick a genuinely harmless real change. Good candidates:
   * fix a typo in a `.md` file
   * add one "What you will learn" card to `index.html`
   * add a comment explaining a confusing line in `styles.css`
   * add one test case to `scripts/validate-contributors.mjs --self-test`
2. Branch, commit, push, open the pull request as normal.
3. Wait for the **Validate** check to go green. This is not optional — the
   automated check is the safety net that makes an unreviewed merge reasonable.
4. Merge it yourself, with **no reviewer assigned and no approval**.
5. Say so in the pull request description: *"Merging without review — YOLO step,
   documentation-only change, Validate is green."*

**Who does what**

* **Opens the issue:** yourself, or skip the issue for this one.
* **Writes the PR:** yourself.
* **Reviews:** nobody. That is the point.
* **Merges:** yourself.

**Repeatable?** No — one-time badge with no tiers. Do it once and go back to
reviewing properly.

**Delay:** up to 24 hours.

**Uncertainty:** low, but note that if **branch protection requiring a review is
already on, this is impossible.** That is why this step comes before repository
hardening. Once everyone has done it, turn protection on and never merge
unreviewed again.

**Doing it honestly:** the change still has to be a real improvement. "YOLO" is
about skipping the review, not about skipping the work.

### 4. Quickdraw — everyone, once

**Requirement (community-sourced):** close an issue or a pull request within
5 minutes of opening it.

**Be honest with yourself about this one.** Of all the achievements here, this
is the one where the natural path is thinnest, because normally you close
something quickly only when you were wrong about it. Two routes below are
genuine. Pick whichever actually happens to you — and if you would rather skip
this achievement than stage the situation, that is a completely reasonable
choice.

**Route A — the duplicate or already-fixed issue (most natural)**

1. You spot something you think is broken. Open an issue describing it.
2. Before you finish reading the code, you realise it is already fixed on
   `main`, or someone already filed it.
3. Close your own issue within 5 minutes with a comment saying which issue
   or which commit it duplicates.

This happens for real, constantly. The trick is to open the issue **when you
notice the problem**, not after you have already finished investigating it.

**Route B — the mistargeted pull request (also very natural)**

1. Open a pull request and immediately notice something wrong with it — it
   targets the wrong base branch, it is missing a file, or you branched from a
   stale `main`.
2. Close it within 5 minutes with a comment explaining the mistake.
3. Fix your branch and open a fresh, correct pull request.

**Who does what**

* You open it, you close it. Nobody else is involved.

**Repeatable?** No — one-time badge, no tiers.

**Delay:** up to 24 hours.

**Uncertainty:** **medium — this is the least certain requirement in this file.**
Most sources say 5 minutes; at least one community post claims 24 hours. Aim for
well under 5 minutes and you satisfy either. Some people also report it not
triggering on the first try; if that happens, wait a full 24 hours before
assuming anything.

**Doing it honestly:** write a real comment when you close it. An issue opened
and closed in silence with no explanation is noise in the issue tracker, and
future-you reading the history will not thank you.

### 5. Galaxy Brain — everyone, over time

**Requirement (community-sourced):** answers accepted in GitHub Discussions.
Tiers at 2 / 8 / 16 / 32.

**This one cannot be rushed, and that is fine.** It needs real questions, which
means it happens naturally while everyone is learning git.

**Setup (repository owner, one-time)**

1. Enable Discussions (Settings → Features → Discussions).
2. Make sure there is a category using the **Question / Answer** format —
   GitHub creates a "Q&A" category by default. **An answer can only be marked as
   accepted in a Q&A-format category.** This is the single most common reason
   Galaxy Brain does not trigger.

**What each participant does**

* **When you get stuck, ask in Discussions instead of a group chat.** Real
  questions that will come up in this project:
  * "I got `CONFLICT (content): Merge conflict in data/contributors.json` — now
    what?"
  * "The Validate check is red but the validator passes on my machine. Why?"
  * "My co-author's avatar is not showing on the merged commit."
  * "Why does the page say 'Could not load the contributor list' when I open
    index.html directly?"
  * "Which no-reply email am I supposed to use, and where do I find it?"
* **When you know an answer, answer it.** Write it properly — enough that the
  next person hitting the same wall can follow it.
* **The person who asked marks the answer as accepted** — using the ✓ button on
  the reply — but only when it genuinely solved their problem.

**Who does what**

* **Asks:** whoever is actually stuck.
* **Answers:** whoever actually knows. The *answerer* earns the achievement, not
  the asker.
* No issue, no pull request, no merge involved.

**Repeatable?** Yes, four tiers: 2 / 8 / 16 / 32 accepted answers.

**Delay:** up to 24 hours after the second accepted answer.

**Uncertainty:** medium. The Q&A-category requirement is well reported but not
officially documented. If nothing appears after 24 hours, check that the
discussion category really is Q&A-format and that the answer really is marked
with the green ✓.

**Doing it honestly:** ⚠️ **Do not fabricate questions.** A discussion where one
person asks a question they already know the answer to, and a friend
immediately "answers" it, is exactly the pattern that gets flagged as
inauthentic activity — it is visible in the timestamps, and people do get called
out for it publicly. Ask when you are actually stuck. If nobody in the group has
ever been stuck, you will not earn this one, and that is an honest outcome.

### 6. Starstruck — repository owner only, and probably not achievable

**Requirement (community-sourced):** a repository you created reaches 16 stars.
Tiers at 16 / 128 / 512 / 4096.

**What to actually do:** each participant may star the repository if they
genuinely find it useful — that is what a star means. With three people, that is
three stars. **It will not reach 16.**

**What not to do:** do not post the repository in unrelated Discussions, issues
or communities asking for stars. Do not create alternate accounts. Do not join
star-exchange schemes. All of these violate
[GitHub's Acceptable Use Policies][aup] on inauthentic activity and put every
account involved at risk. The badge is not worth it.

**Who earns it:** only the person who created the repository. Collaborators get
nothing from this one regardless of how many stars it gets.

**Realistic path:** if this project turns into something genuinely useful and
people find it on their own, the stars follow. That is the only version worth
having.

**Repeatable?** Four tiers, but see above.

**Delay:** up to 24 hours.

**Delay:** up to 24 hours.

**Uncertainty:** low, other than whether a one-time versus recurring sponsorship
both count — that is not clearly documented.
