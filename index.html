      How it works

      Each contribution rotates through four roles, so everyone practises every part of the workflow rather than repeating the same step.

      1. 1

        Someone opens an issue

        A short, specific description of one real improvement — a typo, a contrast fix, a missing card.

      2. 2

        Someone builds it on a branch

        They clone the repo, create a named branch, make the change, and open a pull request that closes the issue.

      3. 3

        Someone reviews it

        A real read-through: does it work, is it readable, does the automated check pass?

      4. 4

        Someone merges it

        The change lands on main, the issue closes automatically, and the roles shift by one.

        What you will learn

        Branching

        Why nobody commits straight to main, and how a branch keeps your half-finished work out of everyone else's way.

        Pull requests

        How to propose a change, describe it well enough that someone can review it, and link it to the issue it solves.

        Review

        How to read someone else's diff, leave a comment that helps rather than nitpicks, and approve with confidence.

        Co-authoring

        How two people share credit for one commit using a Co-authored-by trailer.

        Automation

        How a GitHub Actions workflow checks every pull request before a human even looks at it.

        Fixing mistakes

        Merge conflicts, bad commits and accidental pushes — all recoverable, all covered in the guide.
